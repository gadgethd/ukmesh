### Migration failure and fix

The CI overlay originally probed `pg_isready` without a host, which connects through the local Unix socket. PostgreSQL's entrypoint starts a temporary, socket-only server to execute init scripts. A successful probe at that stage releases `db-migrate`, whose connection URL uses TCP to `timescaledb:5432`. The migration client then fails with `connect ECONNREFUSED` and exits 1. The inconsistent push/PR result is consistent with this timing race; the original failed job did not preserve the migration stderr, so its exact error cannot be recovered retrospectively.

A normal empty-volume run of the pinned database image applied all **67** migrations. To exercise the timing window deterministically, an additional final init SQL hook ran `SELECT pg_sleep(45)`. With the original CI healthcheck, compose marked the database healthy while its health log said `/var/run/postgresql:5432 - accepting connections`; `db-migrate` failed with TCP `ECONNREFUSED` and exited **1**. With the fixed healthcheck, probes to `127.0.0.1:5432` continued to fail until init scripts completed and the final server listened on TCP. The same delayed run exited **0** and its ledger contained **67** migrations.

The fix changes only the CI overlay's probe to `pg_isready -h 127.0.0.1 ...`. The new `scripts/test-ci-db-readiness.sh` holds the temporary server open for 15 seconds, checks the full migration ledger and a final-init marker, and verifies an idempotent second migration run. CI runs it after building the backend image. Smoke failures now emit bounded database and migration logs.
