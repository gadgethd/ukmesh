# Public packet visibility convergence

Migration `062_prefix_visibility_statement_fence.sql` ignores empty prefix
INSERT/UPDATE/DELETE statements, including the empty FK cascade generated by
deleting a public node. An actual direct prefix change or a cascade that removes
prefixes still advances only the public generation. TRUNCATE also fences reads.
Node-trigger prefix maintenance retains migration 056's asynchronous queue.
Alias changes and completed node-scoped worker passes carry materialization
forward only when it was already current; neither repairs an unrelated gap.

Use convergence when the public and materialized generations differ, the
materialized row is missing, or pending/failed work needs a verified full pass.
The command also reports stored flags that differ from current prefix policy.
It operates on **all retained rows in both `packets` and `packet_paths`**, including
compressed history. It does not alter privacy choices, delete rows, migrate the
database, manage services, or refresh derived chart/path snapshots.

## Generation health

The read-only generation reconciler observes a single database snapshot:

| Field | Authoritative source / meaning |
| --- | --- |
| `desiredGeneration` | `public_visibility_state.generation`: current policy generation. |
| `materializedGeneration` | `packet_visibility_materialization_state.visibility_generation`: the stored packet-flag certificate. |
| `appliedGeneration` | Generation admissible to the **global public-read gate**: the materialized generation only when it equals desired and no pending/processing/failed rematerialization exists; otherwise `null`. |

There are two persisted privacy generation records in this repository. Applied
is a derived admission result, not a third durable record, an in-memory cache
stamp, a chart generation or CoreScope's replay cursor. This signal does not
claim to verify a downstream consumer's independently applied generation.
It matches global batch admission (`loadCurrentPublicPrivacyPolicy`); individual
SQL packet reads additionally have node-scoped queue filtering. Pending work
can therefore make this signal unhealthy while unaffected SQL rows remain readable.

`meshcore_privacy_generation_healthy` is a single unlabelled boolean gauge:
`1` means all three reported generations agree and the queue is inactive;
`0` means divergence, missing/invalid state, active work, or a failed/timed-out
observation. Generations remain decimal strings in diagnostics so comparisons
never round large integers; values unsupported by the public reader fail closed.
Each observation emits one JSON log with `event: "privacy_generation_health"`,
the same `healthy` value, a bounded `reason`, the generation triple and
`queueActive`. It contains no node identities, packet data or raw DB errors.

The existing backend and health-worker `/metrics` scrapes drive observations,
independently of dashboard queries or cleanup. The cached `/api/health` overview
also observes the same reconciler and adds the critical incident
`privacy_generation_unhealthy`; public responses expose only its code and
severity. Detailed operator health includes `privacy_visibility`. Liveness and
dependency `/readyz` retain their existing meaning. No new CLI is required.

The probe issues one SELECT: two singleton lookups and queue `EXISTS` using the
status index. It does not count/scan packet history, prefixes, charts or queue
contents. Observations return within two seconds, abort the application's DB
query on timeout, and share at most one pending read across scrapes/health.
If pool acquisition is still draining after timeout, observations remain
unhealthy until it settles; no additional queries accumulate. A later fresh
observation can recover the signal. No generation, timestamp, queue status or
packet flag is changed, and no repair function is called.

The existing Prometheus rule file adds `PrivacyGenerationUnhealthy` when the
backend gauge stays zero **or absent** for five minutes. This holdoff allows
short rematerialization work to settle; the gauge and health incident change
immediately. Alert resolution requires a successful healthy observation.
The existing backend scrape target and rule mount already provide wiring;
activation requires the normal reviewed release of code and monitoring rules.
This change does not deploy or reload either one.

On an alert:

1. Inspect the structured event and internal health detail. A missing relation,
   read failure or absent metric is unavailable evidence, never proof of convergence.
2. For `desired_ahead`/`materialized_ahead` with `queueActive: false`, investigate
   recent policy changes and confirm migration 062 is installed through normal
   operator procedures. An empty queue does not certify packet flags.
3. For `queue_active`, inspect the existing rematerialization backlog/worker
   diagnostics. Do not reset a processing claim or copy generation numbers.
4. An authorized operator may run the read-only inventory described below to
   audit stored flags. Any repair is a separately reviewed maintenance action.
5. Verify the gauge returns to `1`, the health incident clears and the alert
   resolves. This check certifies the generation fence, not correctness of all
   historical flags or downstream replay freshness.

## Inventory and repair

Use the reviewed backend build with migration 062 applied through the normal
migration process. From `backend/`, with `DATABASE_URL` already configured for
the intended database:

```sh
npm run build
npm run privacy:converge
```

The default uses a read-only repeatable-read transaction. JSON reports the
generation pair, queue counts by status, row/mismatch counts for each packet
store, and `needsConvergence`. It prints no packet contents or node identities.
The default statement timeout is 30 seconds; larger inventories may use
`--statement-timeout-ms=900000` (allowed range: 1000–3600000 milliseconds).

Review that the current prefix policy is intentional, especially after an
actual prefix/node deletion. Repair means applying the **current** policy; it
cannot restore a deleted privacy preference. Retaining deleted private
identities would require a separately designed tombstone policy.

Schedule a maintenance window with enough time, free disk and WAL capacity for
a full historical reclassification. Apply blocks node, prefix, alias, queue,
packet and path writers for its transaction. Ordinary readers can continue;
existing privacy fences remain effective until the repair commits. Lock waits
are bounded to five seconds. Deadlock/lock timeout aborts safely; let the
competing transaction finish, inventory again, and retry. Ingest may queue or
retry while locks are held; production load/duration must be evaluated by the
operator before use.

Pass the exact positive `generation` reported by the inventory:

```sh
npm run privacy:converge -- --apply --expected-generation=42
npm run privacy:converge
```

Replace `42` with the reviewed value. Apply defaults to a 15-minute timeout per
statement and accepts the same timeout option. Unknown/duplicate options,
conflicting modes, invalid generations and out-of-range timeouts fail before
connecting. A changed generation or missing public state aborts without writes.
Do not repair by setting the materialized generation manually.

Apply acquires the policy/data locks, checks the reviewed generation, refuses
any `processing` claim, and computes both stored flags from current prefixes and
path validity. It normalizes legacy lowercase hashes before prefix matching.
Unknown path sizes and NULL hops are hidden; nullable validity is never treated
as public or written into a non-null flag.
After complete readback verification, it marks pending/failed work done and
publishes a newly incremented generation pair in the same transaction. Exhausted
failed attempts do not require a manual queue reset. Failure before commit rolls
back flags, queue and generations together; rerun inventory after an uncertain
connection failure. A second successful apply with no
drift changes nothing, including timestamps.

A `processing` row requires waiting for the active worker to finish. An orphaned
processing claim requires operator investigation; this tool does not guess that
a worker is dead, reset claims or manage worker services. After repair, verify
`needsConvergence: false`, equal generations, zero mismatches, and no active
queue entries. Derived snapshots are invalidated by the new generation and
rebuild through their existing workers.

The command uses `SET LOCAL max_parallel_workers_per_gather = 0` because the
CI-pinned TimescaleDB 2.25.1 can report `subplan ... was not initialized` during
a parallel readback after compressed DML. This is transaction local; server and
later pooled-query settings are preserved. The compressed DML budget is removed
only inside the repair transaction, so it cannot silently skip compressed rows.

The runtime image omits npm. The equivalent command there is
`node dist/tools/convergePacketVisibility.js`, with the same arguments and
environment. This document does not authorize deployment or live execution.

## Local reproduction and regression tests

Install the committed backend dependencies, then from the repository root:

```sh
cd backend
npm ci
cd ..
bash scripts/test-privacy-fence.sh
```

The script owns one temporary loopback-only, tmpfs-backed container using the
CI-pinned TimescaleDB image. It creates an isolated test database, executes the
full base schema/migration chain, and stops only its own container on exit. It
does not load application `.env`, application Compose or `DATABASE_URL`.
The test executes rollback SQL to reproduce the old empty cascade (`1/1` to
`2/1`), then upgrades through the real migration runner and proves the fixed
empty cascade stays `1/1`. It also checks real prefix changes, private-node
cascades, public read gates, dry-run with a SELECT-only role, concurrency,
rollback/readback failures, and compressed history above the old 100k budget.

CI runs `npm run test:privacy-integration` against its explicit loopback test
service. Developers may use an owned local fixture through
`TEST_PRIVACY_DATABASE_URL`; the suite creates/drops only its uniquely named
database and creates a uniquely named SELECT-only test role that it removes
after dropping that database. The ordinary unit suite excludes integration tests.

## Rollback

The forward migration is additive; historical migration files are unchanged.
The executable inverse is
`backend/src/db/rollback/062_prefix_visibility_statement_fence.sql`. It has its
own transaction and timeouts, restores the previous statement trigger and
identity function, and leaves packet data, queue data and generation values
alone. It also restores the old false invalidation and alias gap behavior.
The worker's conditional advancement and the convergence command are compatible
with either trigger layout; retain the worker guard when possible.

Do not erase the production migration ledger to roll back. The runner will
retain 062's checksum and will not reapply it automatically; a later forward
rollout needs a reviewed migration or explicit reapplication of the reviewed
SQL. The local fixture removes its own 062 ledger row solely to test a populated
061-to-062 upgrade. Failed migration transactions are also tested to leave the
prior complete trigger layout intact.

Convergence has no automatic data reversal: its only changes are verified
current-policy flags, completed pending/failed work and a new generation.
If privacy policy must change, edit it through the normal authorized path and
rematerialize again. Never roll generations backward or copy stale flags back.
